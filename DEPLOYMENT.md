# Deployment

The public demo runs on **Render** (free plan) against a **Neon** PostgreSQL database:

<https://ai-powered-complaint-management-system-ky8u.onrender.com>

Google Cloud Run is documented further down as an alternative; it is not in use because the
project's billing is not active.

## How it is wired

One Docker web service built from the repository `Dockerfile`: the React build is served by
FastAPI, so the UI and `/api/*` share one origin and the browser needs no configuration.
`render.yaml` is the blueprint. `GET /api/health` always answers 200 and reports the real
database, schema and model state; `GET /api/ready` returns 503 until the service can actually
serve, which is what an orchestrator should poll.

Secrets are never committed. `SESSION_SECRET` is generated by Render and must then be left
alone - changing it signs every visitor out. `DATABASE_URL` (the Neon pooled connection string,
`?sslmode=require`) and `GROQ_API_KEY` are entered once in the dashboard and are marked
`sync: false` in the blueprint so they are never read from the repository.

A free instance sleeps after about 15 minutes idle and takes roughly a minute to wake, so the
first request after a quiet period is slow. That is the plan's behaviour, not a fault.

## Deploying a new revision

Render builds from `main`. With auto-deploy on, merging to `main` is the deploy; otherwise use
**Manual Deploy → Deploy latest commit** in the service. Watch **Events** and **Logs** until the
deploy is Live, then check which revision is actually serving:

```bash
curl -s https://ai-powered-complaint-management-system-ky8u.onrender.com/api/health
```

`revision` in that response is the commit the running instance was built from - Render sets
`RENDER_GIT_COMMIT` for every build, and anywhere else `GIT_COMMIT` does the same job. It is
`null` when the platform did not say, which is the honest answer rather than a guess.

The schema is owned by alembic and upgraded at startup. A failed upgrade does not kill the
service: it serves in a reported degraded state and retries, so `/api/health` tells you what
went wrong instead of the instance disappearing.

## If the service stops responding

A page that hangs with no response at all - rather than Render's loading screen followed by the
app - means the service has no healthy instance. Sync the blueprint, or use **Manual Deploy**,
and check the two secrets above are still set.

### A hang this project has already had, and fixed

- `render.yaml` once requested a paid instance and a paid PostgreSQL add-on, so the blueprint
  could not sync without payment and no instance was ever created. It asks for the free plan now.
- The application connected to its database at startup with no timeout. An unreachable database
  blocked the lifespan, the port was never bound, and the platform router held every request
  open. Startup is now bounded: the schema upgrade is retried later, the process still binds its
  port, and `/api/health` reports `degraded` with the reason. Verified by running the container
  against an unreachable database: the UI is served in 8 seconds.

## Alternative: Google Cloud Run + Neon PostgreSQL

The hosted demo is one Cloud Run service built from the repository `Dockerfile` (React build served
by FastAPI, so the UI and `/api/*` share one origin) and a free Neon PostgreSQL database.
Cloud Run scales to zero when idle and starts a container automatically on the next request.

```
Browser ──► Cloud Run (FastAPI + React build + LangGraph) ──► Groq
                          │
                          └──► Neon PostgreSQL (JSONB, SSL)
```

## 1. Neon (once)

1. Create a free project at https://neon.tech (Postgres 16).
2. Copy the connection string; it looks like
   `postgresql://user:password@ep-xxxx.region.aws.neon.tech/neondb?sslmode=require`.
   The app accepts `postgres://`, `postgresql://` or `postgresql+psycopg://` and keeps the
   `sslmode=require` query parameter. Tables are created automatically on first start.

## 2. Google Cloud (once)

Cloud Run has a monthly free usage allowance (requests, CPU-seconds, memory) that comfortably covers
a demo, but the project must have **billing enabled** (a linked billing account) before Cloud Run
and Cloud Build can be used at all. The region is `us-east1` to sit next to the Neon database
(AWS us-east-2) and to stay in Cloud Run's lowest-price tier.

```bash
gcloud auth login
gcloud config set project <PROJECT_ID>
gcloud services enable run.googleapis.com cloudbuild.googleapis.com artifactregistry.googleapis.com
```

## 3. Deploy from the repository

Build in Cloud Build and deploy in one command (uses the Dockerfile; no local Docker needed):

```bash
gcloud run deploy aivoa-complaint-copilot \
  --source . \
  --region us-east1 \
  --allow-unauthenticated \
  --min-instances 0 --max-instances 3 \
  --memory 512Mi --cpu 1 --concurrency 20 --timeout 120 \
  --set-env-vars GROQ_MODEL=gemma2-9b-it,GROQ_FALLBACK_MODEL=openai/gpt-oss-20b,GROQ_REASONING_EFFORT=low   --set-env-vars SECURE_COOKIES=true   --set-env-vars SESSION_SECRET=<python -c "import secrets; print(secrets.token_urlsafe(32))"> \
  --set-env-vars GROQ_API_KEY=<your Groq key> \
  --set-env-vars DATABASE_URL=<Neon connection string>
```

After the first deploy, set `FRONTEND_URL` to the URL Cloud Run printed (kept for CORS parity;
the UI and API are same-origin so no other frontend configuration exists):

```bash
gcloud run services update aivoa-complaint-copilot --region us-east1 \
  --update-env-vars FRONTEND_URL=https://<service-url>
```

Redeploys keep the existing environment variables; re-run the deploy command without
`--set-env-vars` to ship a new commit, or connect the repository to a Cloud Build trigger
that runs `cloudbuild.yaml` on every push to `main`.

## Cost safety

- **Request-based billing**: CPU is allocated only while a request is being handled (the default;
  `--no-cpu-throttling` is deliberately not used). No background processes run in the container.
- **`--min-instances 0`**: nothing runs, and nothing is billed, while the service is idle. The first
  request after idling starts a container (a few seconds).
- **`--max-instances 3`**: caps concurrent containers so a traffic spike cannot create an
  unexpected bill.
- Neon free tier: compute suspends after inactivity and resumes automatically on the next
  connection; `pool_pre_ping` in `db.py` transparently reconnects.
- Recommended: create a Cloud Billing **budget alert** (e.g. $5/month) in the Google Cloud console
  → Billing → Budgets & alerts.
- No scheduled pings or keep-warm traffic are configured; the service is allowed to scale to zero.

## Verification

```bash
curl https://<service-url>/api/health
# {"database":"ok","groq_configured":true,"configured_model":"gemma2-9b-it",
#  "active_model":"openai/gpt-oss-20b","fallback_reason":"..."}
```

`SESSION_SECRET` must be set and kept stable: sessions are signed with it, so changing it
signs every visitor out, and leaving it unset gives each instance its own ephemeral secret.
Schema changes are applied by alembic at startup (`app/migrate.py`); the application no longer
creates tables implicitly. Take a Neon branch/backup before deploying a migration.

Then open the URL in a browser and run the demo flow (LOG → EDIT → PDF EXTRACT); records are
readable via `GET /api/complaints/{id}` after a redeploy because they live in Neon, not in the
container.
